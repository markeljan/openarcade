# Shared game feedback

OpenArcade uses the server-side `/api/feedback` Vercel Function and a dedicated Neon Postgres database for shared play counts, upvotes, downvotes, and comments. `src/engagement.js` is the browser client. An anonymous, randomly generated browser ID associates a vote with a game; it is not an account or a guarantee against duplicate voting. Reads, votes and play counts stay available without signing in. New public comments require a verified Clerk session and contain 1–280 Unicode code points after trimming. Historical comments remain anonymous and are never assigned to an account. Account comments currently use the safe public label `Player`; no email, account ID or token is returned in comment authors. The API reports unavailable storage explicitly.

The Vercel project needs a sensitive `DATABASE_URL` pointing to the intended database. Apply [`db/feedback-schema.sql`](../db/feedback-schema.sql) once to that dedicated database using its SQL editor. The statements create the three feedback tables and an index if absent; review the target database before running them. The existing OpenArcade Neon integration is linked to Preview and Production. On 2026-10-28, environment metadata still showed these shared target labels and no Development binding; deployment-specific Neon branch isolation could not be verified with the available integration permissions. Treat previews as potentially sharing production feedback until actual Neon branch/endpoint identities establish isolation. Do not run mutation, reset or cleanup tests on them. Use the existing integration's Preview Branching or a confirmed isolated branch; never delete production comments/votes. See [operations](OPERATIONS.md) for the target record and release sequence.

`npm run dev` and `npm run preview` serve the Vite frontend only; they do not execute Vercel Functions, so feedback is unavailable there. To test the function locally, use `vercel dev` with the project linked and a Development-targeted database connection supplied through Vercel's environment workflow. Use an isolated test database for development when practical. Never commit credentials or print connection strings in logs. A new deployment is required for environment variable changes to reach a deployed function.

Run `node --test tests/feedback-api.test.js tests/engagement-client.test.js` for the local contract tests. These tests use a simulated query layer; a deployed endpoint connected to Postgres needs a separate end-to-end check across distinct browser identities.

## Clerk setup and migration ordering (S03)

Reuse the existing OpenArcade Clerk application. Do not create a second app. S11 coordinates the existing development/production instances and allowed origins; S01 controls deployment and release. The confirmed production application origin is `https://openarcade.io`. Configure the exact isolated preview origin separately; do not use a wildcard for every `vercel.app` deployment or infer trusted origins from incoming request headers.

Only `VITE_CLERK_PUBLISHABLE_KEY` enters the static browser build. Server environment names are `CLERK_ISSUER`, `CLERK_AUTHORIZED_PARTIES`, and either `CLERK_JWT_KEY` or `CLERK_SECRET_KEY`. Match the issuer/key and publishable key to the same Clerk instance. `CLERK_AUTHORIZED_PARTIES` is a comma-separated list of exact application origins; `CLERK_ISSUER` is the exact Clerk Frontend API origin. See [the identity contract](auth-contract.md). Never copy production secret values into Vite-prefixed variables. Environment changes require rebuilding/redeploying the appropriate target.

Apply `db/feedback-schema.sql`, then the additive [comments migration](../db/comments-auth-schema.sql), to the intended isolated preview database before deploying the new feedback handler. Verify preview there before S01 authorizes the equivalent production migration and deployment. The new handler reads `removed_at` and author columns, so the migration must precede that handler. It does not rewrite historical bodies/ownership. Environment labels do not prove database isolation: assume preview may share production and do not run test writes, resets or cleanup until S11 proves isolation. Follow S11's `docs/OPERATIONS.md` runbook when it lands. Rollback can keep the additive columns/tables and restore the previous deployment.

Comment writes use only `Authorization: Bearer` session tokens. The server verifies signature, expiry, issuer, authorized party and session claims through `server/auth.js`. A visitor UUID or supplied `userId`/name never proves identity. The server enforces a 2,048-byte UTF-8 JSON body limit for parsed and raw requests. It consumes a durable per-account budget of 5 comments per minute and 50 per 24-hour window in the same SQL statement as insertion; limits are global across games and shared function workers. Anonymous voting/play counting retains its previous behavior. A rate limit is an abuse control, not proof that a person owns only one account.

## Browser integration for S04 and S02

`src/auth.js` exports `auth` and injectable `createAuthClient`. `auth.ready`/`initialize()` resolve without throwing when configuration/loading fails; call `initialize()` again to retry a temporary load failure. `getState()` returns `{status,user}` with `loading`, `signed-out`, `signed-in`, or `unavailable`; a signed-in user is `{id,displayName}`. `subscribe(listener)` sends the current state immediately and returns an unsubscribe function. `getToken()` requests a fresh session token and returns a string or null, discarding a token if the user/session changes while it loads. The application does not persist tokens. Auth loading/failure must never gate free gameplay.

`signIn()` opens Clerk's body modal for the gallery header. Inside the native player dialog, use `await auth.mountSignIn(div)` to mount inside its top layer; the result is an idempotent disposer. These promises mean opened/mounted, not authentication complete. Use `subscribe` to detect success and call the disposer on success/cancel/player close. S04 owns an accessible cancel control, focus restoration and pause composition. Mounting uses hash routing, explicitly requests `oauthFlow:'popup'`, and captures the same-game return URL beforehand. A provider popup does not guarantee the main tab will never navigate: successful sign-in/sign-up return redirects and session setup may still require it. S02/S04 must preserve pending scores durably before sign-in; a memory-only queue is not redirect-safe and must not silently proceed as if it were. Do not suppress Clerk's required navigation globally. `signOut()` signs out without clearing pending scores or comment drafts. See Clerk's [JavaScript quickstart](https://clerk.com/docs/js-frontend/getting-started/quickstart) and [mount/unmount reference](https://clerk.com/docs/js-frontend/reference/components/authentication/sign-in).

`getCommentDraft(gameId)`, `saveCommentDraft(gameId,text)` and `clearCommentDraft(gameId,expectedText)` preserve exact text per game in tab session storage with an in-memory fallback. Save on input and before sign-in, restore on game selection/reload, and clear only after an acknowledged write with matching text. Blocked storage cannot preserve drafts across a full reload; it still preserves them while the page stays open. `addComment(gameId,text)` obtains a token, saves the draft before its request, and clears only that matching draft on success. It never auto-posts after login. S02 keeps score queues independently and clears only acknowledged saves.

Feedback errors carry `.status` and `.code`: `sign_in_required` (401), `auth_unavailable` (503), `comment_rate_limited` (429), `body_too_large` (413), and `feedback_unavailable` (503, or status 0 for transport failure). Preserve drafts on errors, disable submit while pending, offer retry, and guard late callbacks against another selected game. When Clerk cannot obtain a token for a signed-in/loading/unavailable state, the client reports unavailable instead of treating the failure as sign-out. Safe author shape is `{kind:'account'|'anonymous',displayName}`. Render both author and body using `textContent`, never HTML.

S04 supplies keyboard/touch-accessible help with the exact copy: “Feedback may be used by AI agents to improve gameplay and fix bugs.” This does not claim an automatic improvement pipeline exists.

## Removal and checks

S11's lightweight moderation path is parameterized SQL on the reviewed target: `UPDATE arcade_comments SET removed_at=now() WHERE id=$1`. Public reads exclude removed rows. A trusted operator can reverse a mistaken removal with `removed_at=NULL`. Keep operator access server-side; no unauthenticated admin endpoint is introduced. The handler logs only the stable `feedback_unavailable` code, with no request text, thrown error, connection string, token or claims.

Focused checks: `node --test tests/server-auth.test.js tests/auth-client.test.js tests/feedback-api.test.js tests/engagement-client.test.js`. RSA tests exercise the real Clerk verifier; mock SQL tests establish request/parameter behavior only. Release still needs a configured preview check of anonymous reads/rejected spoofed writes, two real Clerk users, expired sessions, old comment reads, safe text display, cancel/redirect draft recovery, sign-out, in-flight controls and database limits. A plain Vite run does not execute the Vercel Function and cannot establish those boundaries.
